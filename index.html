写了这么多年后端,我越来越觉得"技术债"这个词被误用了。大多数人把它当成一句道德指控——谁写了烂代码,谁就欠了债,迟早要还。但真正在一线做过大型重构的人都知道,技术债更像是一种"融资":你用未来的确定性,换取今天的交付速度。问题从来不是"要不要借债",而是"借了之后有没有在还,利率是不是失控了"。 第一类债是主动的、清醒的。为了赶一个明确的窗口期,你决定先硬编码几个配置、跳过一部分边界测试、用一张宽表扛住早期的查询。你知道它丑,你甚至在代码里写了 TODO 和 issue 链接。这类债是健康的,因为它是被记账的——只要业务活下来了,你回头就能连本带利还上。真正危险的是第二类:无意识的债。团队里没人知道某个模块为什么这么写,当初拍板的人早已离职,文档停留在两年前,每次改动都像在拆一颗不知道还有没有电的雷。这种债不产生利息,它直接产生恐惧,而恐惧会让整个团队丧失重构的勇气。 我带团队时定过一条规矩:任何一次"我们先这样,以后再优化"的决定,都必须落到一个有 owner、有截止时间的条目上。没有 owner 的技术债不叫债,叫遗产;没有截止时间的优化不叫计划,叫许愿。这条规矩执行下来最大的收获,不是我们还掉了多少债,而是团队开始诚实地面对"我们到底在拿什么换什么"。很多时候讨论到一半会发现,那个所谓的窗口期根本不存在,是我们自己臆想出来的压力。 还债的时机也很讲究。新手工程师喜欢挑一个风和日丽的下午,专门开一个"重构分支",然后花两周把整个模块推倒重来。这几乎总是灾难:重构分支跟主干越漂越远,合并时冲突堆积如山,期间线上还在改 bug,最后要么放弃要么带着一堆没验证的改动硬着头皮上线。我更信奉"顺路重构"——每次因为需求碰到那块脏代码,就顺手把它擦干净一点点。加一个测试、抽一个函数、给一个变量改个人话名字。单次改动小到 code review 五分钟能过,风险可控,而且它绑定在真实需求上,不需要单独向老板申请预算。半年下来,那些最常被改动的热点区域自然会变干净,而那些从来没人碰的冷角落——说明它也没那么重要,可以继续躺着。 衡量技术债还有个反直觉的点:不是所有债都值得还。有些代码丑陋但稳定,三年没出过问题,输入输出边界清晰,那它就是一个黑盒,你该做的是给它包一层清晰的接口然后永远别打开它。把有限的重构精力花在这种地方,纯属用工程师的洁癖消耗公司的钱。真正该还的债,是那些"改动频繁 + 质量低下"同时成立的模块——它们既是 bug 的温床,又是迭代速度的瓶颈,ROI 最高。我习惯用 git log 拉出过去半年改动最频繁的文件,再交叉对比缺陷率,排在前面的就是重构清单,其余的一律不碰。 最后一点,也是我踩了很多年坑才想明白的:技术债的本质是沟通债。绝大多数烂代码不是因为工程师水平不行,而是因为写它的人和用它的人之间、当时的团队和现在的团队之间,信息没有传递到位。所以对抗技术债最划算的投资,往往不是重写代码,而是补一份让下一个人五分钟能读懂"为什么这么设计"的文档,是在关键决策点留下一段 commit message 解释权衡,是让新人 onboarding 时有人能讲清楚系统的历史包袱从何而来。代码会过时,但"为什么"几乎永远有价值。等哪天你发现自己在给一段三年前的代码写解释时,依然认同当初的取舍,那才说明你当年借的那笔债,利率是划算的。

工作十年，我越来越相信：一个工程师的成长曲线，不是由他「能写多复杂的代码」决定的，而是由他「敢删多少代码」决定的。刚入行时，我们用增加来证明自己——加功能、加抽象、加配置项、加一层又一层的间接。那时最怕别人觉得方案太简单。后来才慢慢明白，简单不是能力的下限，而是上限：你要先把一个问题真正理解透，才有底气把它压缩成一段读起来平平无奇、却恰好覆盖所有边界的代码。真正难的从来不是把系统做大，而是在它长大之后，还能一刀刀把不再需要的部分削掉，让它保持一个人脑能装得下的形状。所以现在做 code review，我最欣赏的一类改动，是那种 diff 里删除远多于新增、功能却一点没少的提交——它背后往往是一次真正想清楚了的重构。

chronicle-engine
一个面向文字冒险与叙事游戏的确定性剧情引擎。核心思路是把「内容」「引擎」「AI 叙述」三层彻底解耦：内容层用声明式脚本定义所有可能的节点、分支与后果；引擎层是唯一能修改世界状态（WorldState）的地方，所有改动都走事务，支持检查点（Checkpoint）与回溯；AI 层只负责解析玩家的自由输入并做文本润色，绝不允许直接写状态。为了保证「同样的操作必然得到同样的结果」，随机性不是全局的，而是从每个动作的签名派生出子随机流，因此存档回放、并发模拟、单元测试都能得到逐字节一致的输出。附带一个 story-checker 脚本，可在 CI 里自动检查泄露的占位符 ID、走不通的死路、以及不满足确定性的分支。
